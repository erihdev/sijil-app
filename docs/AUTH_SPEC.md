# مواصفة تحصين أرقام الدخول — سجلي

الملف المنفِّذ: `js/auth.js` (يصدّر `window.SIJIL_AUTH`). لا يعتمد على أي مكتبة، ويعمل سحابياً وتجريبياً بالمنطق نفسه.

## 1. المشكلة

- بصمة رقم الدخول `sha256(الرقم|معرّف المعلم|"sijil1448")` كانت مخزّنة في `teachers/{tid}.pinHash`.
- `teachers` **مقروءة لأي جهاز مصادَق**، والموقع يصادق كل زائر مجهولاً تلقائياً. فأي زائر ينسخ بصمات المعلمين كلها في طلب واحد، ثم يجرّب عليها ملايين الأرقام **على جهازه بلا اتصال** — أربع خانات تُكسر في أجزاء من الثانية.
- والقواعد القديمة كانت تسمح لأي جهاز مصادَق بكتابة `pinHash` جديدة لأي معلم غير مدير ⇒ استيلاء كامل على حساب معلم.

## 2. النموذج الجديد

| المسار | المحتوى | القراءة | الكتابة |
|---|---|---|---|
| `pins/{h}` | `{tid, ts}` — و`h` هي البصمة نفسها | `get` نعم · **`list` لا** | إنشاء بشرط، لا تحديث، حذف بإثبات |
| `pinreq/{tid}` | `{h, old?, by?, byPin?, ts, tn}` | **ممنوعة للجميع** | إنشاء/تحديث بإثبات، حذف لأي مسجّل |
| `teachers/{tid}` | `+ reg: bool` · `+ pt: number` | كما هي | `pinHash` تُزال ولا تُكتب بقيمة جديدة أبداً |

- **لا تبقى أي بصمة في مستند يمكن تصفّحه.** معرّف المستند هو البصمة، ومنع `list` يعني أن أحداً لا يعرف وجود بصمة إلا إن عرف رقمها أولاً.
- **`reg`** = «سُجّل رقم هذا المعلم في `pins`»، ولا تعود `false` أبداً (قاعدة).
- **`pt`** = ختم الرقم الحالي (رقم لا يفشي شيئاً). الدخول يشترط `pins/{h}.ts == teachers/{tid}.pt` حين يكون `pt` موجوداً.
  هذا الختم هو ما يُبطل الرقم القديم **فوراً** حتى لو تعذّر حذف مستند بصمته — وهو ضروري لإعادة تعيين المدير، لأن المدير بعد الترحيل لا يعرف رقم المعلم القديم فلا يستطيع حساب بصمته ولا حذفها.
- **قناة الإثبات `pinreq/{tid}`** هي البديل عن الخادم: إنشاؤها نفسه هو الإثبات، ووجودها هو ما يأذن بإنشاء بصمة جديدة وبختم مستند المعلم.

### الأختام لا تتصادم
`ts` الجديد = `Date.now()` + تشتيت عشوائي دون الثانية، ثم يُرفع ليكون أكبر من ختم المعلم الحالي وأكبر من كل ختم صنعته الجلسة. بدون هذا الشرط قد يتساوى ختم رقم قديم مع ختم رقم جديد فيبقى القديم صالحاً — وهو خلل حقيقي ظهر في الاختبار وأُصلح.

## 3. الواجهة `window.SIJIL_AUTH`

| الدالة | ترجع |
|---|---|
| `hash(pin, tid)` | البصمة (نفس صيغة الدخول القديمة — لا تغيير في الملح) |
| `verify(tid, pin)` | `{ok, via, weak}` أو `{ok:false, err}` · `via`: `pins` / `legacy` / `demo` / `offline` |
| `changePin(tid, oldPin, newPin)` | `{ok, ts, weak}` أو `{ok:false, err}` |
| `resetPin(targetTid, adminTid, adminPin, newPin)` | مثلها — المدير يثبت **رقمه هو** |
| `registerFirst(tid, pin)` | مثلها — لمعلم لا رقم له |
| `migrateAll(onStep)` | `{total, done, skipped, failed[]}` — ترحيل جماعي |
| `isRegistered(tid)` · `PIN_RE` · `STRONG_RE` · `MSG` · `flush()` | مساعدات للواجهة |

`weak: true` تعني أن الرقم أقل من ٦ خانات — تُعرض للمستخدم نصيحة `MSG.advice` ولا يُمنع.

**تحديث ٦ سبتمبر ٢٠٢٦:** كل رقم **جديد** لا يُقبل دون ٦ خانات (`STRONG_RE` في `registerFirst` و`changePin` و`resetPin`، ورسالة `MSG.short`)، ونماذج اللوحة تقول «٦–١٢ رقماً». أمّا **الدخول** فيبقى يقبل ٤ خانات (`PIN_RE`) حتى لا يُمنع معلم رقمُه القديم أقصر.
كل نصوص الأخطاء عربية جاهزة للعرض في `SIJIL_AUTH.MSG`.

## 4. الترتيب الآمن (لا يُقفل حساب أبداً)

لكل تغيير أو إعادة تعيين، بهذا الترتيب حصراً:

1. أنشئ `pinreq/{tid}` (الإثبات).
2. أنشئ `pins/{البصمة الجديدة}` **وأعد قراءتها للتأكد من وصولها فعلاً**.
3. اختم مستند المعلم `{reg:true, pt:ts, pinHash: حذف}`.
4. احذف `pins/{البصمة القديمة}` (إن كانت معروفة).
5. احذف `pinreq/{tid}`.

- انقطاع بعد (1) أو أثناء (2): لا شيء تغيّر، والرقم القديم يعمل.
- فشل (3) بعد نجاح (2): **تراجع** — تُحذف البصمة الجديدة (القاعدة تسمح لأن `pinreq.h` تساويها) ثم تُحذف القناة، فلا يبقى رقمان صالحان، والرقم القديم يعمل. الرسالة: «لم يكتمل التغيير — رقمك القديم لا يزال يعمل، أعد المحاولة».
- فشل (4): الرقم القديم أُبطل بالختم أصلاً؛ يبقى مستند يتيم غير مؤذٍ ولا يمكن تصفّحه.

## 5. الدخول بلا إنترنت

بعد أول دخول ناجح على الجهاز يُحفظ في `localStorage` تحت `sijil.auth.local` **إثبات مشتق بـ PBKDF2** (١٥٠ ألف دورة، ملح عشوائي ١٦ بايت) لا البصمة نفسها — فمن يفتح تخزين الجهاز لا يجد ما يُخمَّن عليه بسرعة. أربعة حسابات كحد أقصى، والكتابة متسلسلة حتى لا يمحو حفظٌ آخر. متصفح بلا PBKDF2 ⇒ لا إثبات محلي أصلاً (ولا بصمة مكشوفة).

## 6. نص القواعد المطلوب حرفياً

### 6-أ · دوال مشتركة (تُضاف مرة واحدة داخل `match /databases/{database}/documents`)

```
    // ── أرقام الدخول: دوال مشتركة ──
    function isHash(x) { return x is string && x.matches('^[0-9a-f]{64}$'); }
    function tHas(tid)  { return exists(/databases/$(database)/documents/teachers/$(tid)); }
    function tDoc(tid)  { return get(/databases/$(database)/documents/teachers/$(tid)).data; }
    function pinHas(h)  { return exists(/databases/$(database)/documents/pins/$(h)); }
    function pinDoc(h)  { return get(/databases/$(database)/documents/pins/$(h)).data; }
    function reqHas(tid){ return exists(/databases/$(database)/documents/pinreq/$(tid)); }
    function reqDoc(tid){ return get(/databases/$(database)/documents/pinreq/$(tid)).data; }
```

### 6-ب · المجموعتان الجديدتان

```
    // ── pins/{h}: البصمة نفسها هي معرّف المستند {tid, ts} ──
    //    get نعم (الدخول يقرأ بصمة واحدة يعرف رقمها)، list لا أبداً (فلا تُتصفَّح البصمات).
    //    الإنشاء: أول تسجيل لمعلم لم يُسجَّل، أو بقناة إثبات تحمل البصمة نفسها.
    //    التحديث ممنوع (لا تُنقل بصمة من معلم إلى آخر)، والحذف بقناة إثبات فقط.
    match /pins/{h} {
      allow get: if signedIn();
      allow list: if false;
      allow create: if signedIn()
          && h.matches('^[0-9a-f]{64}$')
          && request.resource.data.keys().hasOnly(['tid', 'ts'])
          && request.resource.data.tid is string
          && request.resource.data.tid.matches('^t[0-9]{2,3}$')
          && request.resource.data.ts is number
          && tHas(request.resource.data.tid)
          && (tDoc(request.resource.data.tid).get('reg', false) != true
              || (reqHas(request.resource.data.tid)
                  && reqDoc(request.resource.data.tid).h == h));
      allow update: if false;
      allow delete: if signedIn()
          && reqHas(resource.data.tid)
          && (reqDoc(resource.data.tid).h == h
              || reqDoc(resource.data.tid).get('old', '') == h);
    }

    // ── pinreq/{tid}: قناة إثبات مؤقتة، لا يقرأها أحد (exists/get داخل القواعد لا تخضع لقواعد القراءة) ──
    //    (أ) المعلم يثبت معرفته رقمه الحالي: pins/{old} موجودة وtid فيها هو صاحب الطلب.
    //    (ب) المدير يثبت معرفته رقمه هو: pins/{byPin} موجودة وtid فيها هو by، وby مديرٌ فعلاً.
    match /pinreq/{tid} {
      allow read: if false;
      allow create, update: if signedIn()
          && tid.matches('^t[0-9]{2,3}$')
          && request.resource.data.keys().hasOnly(['h', 'old', 'by', 'byPin', 'ts', 'tn'])
          && isHash(request.resource.data.h)
          && request.resource.data.ts is number
          && request.resource.data.tn is string && request.resource.data.tn.size() <= 80
          && ((isHash(request.resource.data.get('old', ''))
               && pinHas(request.resource.data.old)
               && pinDoc(request.resource.data.old).tid == tid)
              || (isHash(request.resource.data.get('byPin', ''))
                  && request.resource.data.get('by', '').matches('^t[0-9]{2,3}$')
                  && pinHas(request.resource.data.byPin)
                  && pinDoc(request.resource.data.byPin).tid == request.resource.data.by
                  && tHas(request.resource.data.by)
                  && tDoc(request.resource.data.by).get('admin', false) == true));
      allow delete: if signedIn();
    }
```

### 6-ج · تعديل `teachers/{tid}` القائم

في `teacherShape()` أضِف `'reg'` و`'pt'` إلى `hasOnly` وأضِف سطري النوع:

```
      return request.resource.data.keys().hasOnly(['name', 'subject', 'mob', 'phone', 'classes', 'pinHash', 'admin', 'lead', 'reg', 'pt', 'ts'])
          ...   // بقية الشروط كما هي بلا تغيير
          && (!('reg' in request.resource.data) || request.resource.data.reg is bool)
          && (!('pt' in request.resource.data) || (request.resource.data.pt is number && request.resource.data.pt > 0));
```

استبدل `allow create` و`allow update` بهذين (المرحلة النهائية):

```
      // معلم جديد: بلا صلاحية مدير، وبلا بصمة في المستند (البصمة تذهب إلى pins)، وبلا علم تسجيل ولا ختم
      allow create: if signedIn() && tid.matches('^t[0-9]{2,3}$') && teacherShape()
          && request.resource.data.get('admin', false) == false
          && request.resource.data.get('pinHash', '') == ''
          && request.resource.data.get('reg', false) == false
          && !('pt' in request.resource.data);
      allow update: if signedIn() && tid.matches('^t[0-9]{2,3}$') && teacherShape()
          // صلاحية المدير لا تتغيّر أبداً
          && request.resource.data.get('admin', false) == resource.data.get('admin', false)
          // البصمة القديمة تُزال ولا تُكتب بقيمة جديدة أبداً (هذا وحده يُنهي الاستيلاء على حساب معلم)
          && (request.resource.data.get('pinHash', '') == resource.data.get('pinHash', '')
              || request.resource.data.get('pinHash', '') == '')
          // علم التسجيل لا يعود false
          && (resource.data.get('reg', false) == false
              || request.resource.data.get('reg', false) == true)
          // الختم لا يتغيّر إلا بقيمة قناة الإثبات نفسها ⇒ لا يستطيع زائر تعطيل حساب بختم عشوائي
          && (request.resource.data.get('pt', 0) == resource.data.get('pt', 0)
              || (reqHas(tid) && request.resource.data.get('pt', 0) == reqDoc(tid).ts));
      allow delete: if false;
```

### 6-د · ما هو منشور فعلاً منذ ٦ سبتمبر ٢٠٢٦ (انتهت المرحلة الانتقالية)

حُذف السماح الانتقالي: لم تعد أي بصمة تُكتب في `teachers/{tid}` لا في الإنشاء ولا في التحديث، لأحدٍ كان — معلماً أو مديراً. والمحو مسموح بشرطين معاً:

```
      && (request.resource.data.get('pinHash', '') == resource.data.get('pinHash', '')
          || (request.resource.data.get('pinHash', '') == ''
              && resource.data.get('reg', false) == true
              && !(isHash(resource.data.get('pinHash', ''))
                   && pinHas(resource.data.get('pinHash', '')))))
```

الشرط الثاني (`!pinHas`) ليس تزيّداً، وهو أهم سطر في الملف كله:

> **بصمةٌ نُشرت في مستند مقروء ولها مستند `pins` حيّ ليست سرّاً، بل هي مفتاح.**
> من قرأها يستطيع أن يقدّمها في `pinreq.old` فتقبلها القواعد إثباتاً «أنه يعرف رقمه الحالي»، ثم يُنشئ بصمة جديدة من رقمه هو ⇒ استيلاء كامل على الحساب بلا معرفة الرقم.
> لذلك: (١) `pinreq` ترفض أي بصمة ما دامت منشورة في مستند المعلم (`tDoc(tid).pinHash != old`، ومثلها `byPin`)، (٢) والمحو ممنوع ما دام لها مستند `pins` حيّ — وإلا محاها المهاجم بنفسه ليرفع الحماية ثم استعمل نسخته المحفوظة.
> ⇒ **العلاج الوحيد لبصمة نُشرت هو تعيين رقم دخول جديد لصاحبها**، فيموت مستند `pins` القديم وتُمحى البصمة تلقائياً عند أول دخول (`dropStaleHash`).

> ملاحظة تكلفة: كل `exists`/`get` داخل القواعد قراءة محسوبة. أطول سلسلة هنا ٣ قراءات لكل طلب كتابة، والحد ١٠ — بفارق مريح.

## 7. خطة الترحيل

| # | الخطوة | من يُنفّذها | التحقق |
|---|---|---|---|
| ١ | انشر القواعد **الانتقالية** (٦-أ + ٦-ب + ٦-ج بسطر ٦-د) | عميل القواعد | تُطبع `Deploy complete`، والتطبيق القديم لا يزال يعمل |
| ٢ | ادمج `js/auth.js` وطلبات الدمج (القسم ٩) وانشر التطبيق | عميل الدمج | الدخول يعمل، وأول دخول لكل معلم يُرقّي حسابه صامتاً |
| ٣ | اترك أسبوعاً: كل من دخل تُنقل بصمته تلقائياً إلى `pins` وتُمسح من مستنده | — | «حالة التسجيل» في لوحة المدير |
| ٤ | من لوحة المدير: زر «🔐 ترحيل أرقام الدخول» (`migrateAll`) لمن لم يدخل بعد | المدير | التقرير يعيد `done` و`failed[]` |
| ٥ | تحقق أنه لا `pinHash` باقية في أي مستند معلم | المدير | لوحة المدير تعرض العدد |
| ٦ | انشر القواعد **النهائية** (بحذف سطر ٦-د) | عميل القواعد | تُطبع `Deploy complete` |

الترتيب مقصود: القواعد أولاً لأنها **تسمح ولا تمنع** في المرحلة الانتقالية، فلا تنكسر الأجهزة القديمة. ولا تُنشر القواعد النهائية قبل أن يُصفَّر عدّاد `pinHash`.

### 7-ب · ما بقي بعد نشر القواعد النهائية (٦ سبتمبر ٢٠٢٦)

الترحيل رفع `reg=true` ولم يمحُ `pinHash`، فبقيت البصمات منشورة. القواعد النهائية تمنع أي كشف جديد، لكنها لا تُعيد سرّية ما نُشر. المتبقي عمل لصاحب المشروع لا يقدر عليه العميل:

| # | الخطوة | من يُنفّذها | التحقق |
|---|---|---|---|
| ١ | انشر ملفات التطبيق الجديدة (`index.html?v=49` وما بعده) | صاحب المشروع | تغيير رقم الدخول ينجح لمعلم بصمته منشورة (بالإصدار القديم يفشل برسالة «لم يكتمل التغيير») |
| ٢ | من كونسول Firebase: احسب بصمة رقم جديد للمدير، وأنشئ `pins/{البصمة} = {tid, ts}`، ثم احذف حقل `pinHash` من مستنده | صاحب المشروع | المدير يدخل بالرقم الجديد، ويستطيع «🔑 إعادة تعيين رقم الدخول» لأي معلم |
| ٣ | عيّن **رقماً جديداً لكل معلم** بقيت بصمته منشورة (بطاقته تعرض «⚠️ يحتاج رقماً جديداً») | المدير من اللوحة | الشارة تتحول إلى «✅ سجّل هويته»، وتُمحى `pinHash` تلقائياً عند أول دخول له |

> ما دامت الخطوة ٣ لم تكتمل لمعلم، فرقمه في حكم المكشوف: بصمته منشورة، وست خانات تُخمَّن على أي جهاز بلا اتصال في ثوانٍ.

## 8. خطة التراجع

- **تراجع فوري بلا فقد**: أعِد نشر ملف القواعد السابق (محفوظ في `firestore.rules` و«قواعد أمان Firestore.rules» على سطح المكتب) وأعِد نشر `index.html` بلا سطر `js/auth.js`. الأرقام القديمة لا تعود تعمل لمن رُحِّل حسابه (مُسحت `pinHash`) — لذلك:
- **قبل الخطوة ٢ خذ نسخة**: زر «⬇️ تصدير» في لوحة المدير يصدّر المعلمين؛ صدّر نسخة **تحوي `pinHash`** واحفظها خارج المستودع (لا تُرفع إلى git). الاستعادة تُعيد البصمات إلى مستندات المعلمين، وتعمل ما دامت القواعد الانتقالية منشورة.
- **تراجع جزئي (الأرجح عملياً)**: لا حاجة للتراجع أصلاً — من فشل ترحيله يبقى برقمه القديم يعمل، لأن `verify` يسقط إلى `pinHash` ما دامت `reg != true`.
- **معلم عَلِق**: `resetPin` من المدير يفتح أي حساب في أي حالة (المدير يثبت رقمه هو).
- **رقم المدير**: صار قابلاً للتغيير من داخل التطبيق (بإثبات رقمه الحالي) — لم يعد يحتاج كونسول Firebase. وإن ضاع رقم المدير كلياً: احذف `teachers/{tid}.reg` و`pt` من كونسول Firebase، ثم `registerFirst` من التطبيق.

## 9. ما يبقى مكشوفاً (بصراحة)

1. **التخمين عبر الشبكة**: البصمة لم تعد تُنسخ، لكن يبقى بإمكان زائر أن يجرّب أرقاماً واحداً واحداً بقراءة `pins/{h}` لكل محاولة. أربع خانات = ١٠ آلاف طلب. الفارق عن السابق هائل (كان بلا اتصال وبسرعة الجهاز)، لكنه ليس صفراً. المخفّفات: App Check مفعّل (كل طلب يحتاج رمز reCAPTCHA من نطاقنا)، والتوصية برقم ٦ خانات فأكثر (مليون احتمال) — لذلك تُعيد الدوال `weak:true` لتنبيه المستخدم. **التوصية: اجعل الأرقام المولَّدة ٦ خانات** (زر «🎲 توليد» يولّدها ٦ خانات فعلاً اليوم).
2. **اختطاف معلم لم يُسجَّل بعد**: القاعدة تسمح بإنشاء أول بصمة لمن `reg != true` بلا إثبات (وإلا تعذّر تسجيل أول معلم). فبين إنشاء حساب المعلم وتسجيل رقمه توجد نافذة يستطيع فيها زائر تثبيت رقم يعرفه هو. المخفّف: المدير يعيّن الرقم في اللحظة نفسها التي يضيف فيها المعلم (نافذة ثوانٍ)، و`resetPin` يستعيد الحساب دائماً.
3. **تعطيل مؤقت (لا استيلاء)**: زائر يستطيع رفع `reg` إلى `true` ومسح `pinHash` لمعلم لم يُسجَّل، فيمنعه من الدخول حتى يعيد المدير تعيين رقمه. ويستطيع حذف `pinreq` أثناء تغيير جارٍ فيفشل التغيير (والرقم القديم يبقى يعمل). كلاهما إزعاج قابل للإصلاح فوراً، لا اختراق — بخلاف الوضع القائم اليوم الذي يسمح بالاستيلاء الكامل.
4. الإغلاق التام لهذه الثلاثة يحتاج مصادقة حقيقية أو Cloud Function (خطة Blaze) — خارج نطاق هذا الإصدار.

## 10. ما تم اختباره فعلياً

الوضع التجريبي على `http://localhost:8954/index.html?demo`، فوق **محاكي يطبّق نص القواعد أعلاه حرفاً بحرف** (`scratchpad/rulesim.js`)، على مقاسي ١٢٠٠×٨٠٠ و٣٩٠×٨٠٠: **٤٢ تحققاً، كلها ناجحة، وصفر أخطاء console**.

- الدخول ببصمة قديمة يرقّي الحساب صامتاً · الدخول التالي عبر `pins` · الرقم الخاطئ يُرفض.
- تغيير الرقم: الجديد يعمل، والقديم لا، وبصمته حُذفت، والقناة حُذفت، والختم كُتب.
- أول تسجيل · لا أول تسجيل مرتين.
- إعادة تعيين المدير: تنجح، والرقم القديم أُبطل **بالختم** ولو بقي مستند بصمته · رقم مدير خاطئ يُرفض ولا يغيّر شيئاً · غير المدير يُرفض.
- مرفوض بالقواعد: إنشاء بصمة لمعلم مسجّل بلا إثبات · كتابة بصمة جديدة في مستند المعلم · إرجاع `reg` إلى `false` · تغيير `pt` بلا إثبات · قناة بلا إثبات · معلم عادي يدّعي أنه مدير · حذف بصمة بلا إثبات.
- لا `pinHash` باقية في أي مستند معلم بعد الترحيل.
- انقطاع بين إنشاء البصمة والختم: الرقم القديم يعمل، والجديد تراجَع، ولا قناة معلّقة.
- الدخول بلا إنترنت بالإثبات المحلي، والرقم الخاطئ يُرفض، ولا بصمة خام في تخزين الجهاز.

## 11. الترحيل الحي — ما نُفِّذ فعلاً على مدرسة تعمل (٦ سبتمبر ٢٠٢٦)

نُفِّذ الترحيل بصلاحية مالك المشروع عبر Firestore REST (لا من المتصفح)، والقواعد المنشورة يومها هي
نصّ `firestore.rules` الحالي حرفاً بحرف (تحقّقنا بمقارنة الملف بالمجموعة المنشورة فعلاً: لا فرق).

**الحالة قبل الترحيل**: ٢٤ مستند معلم، كلها تحمل `pinHash` صالحة، ولا واحد منها `reg = true`،
ومجموعتا `pins` و`pinreq` غير موجودتين أصلاً (صفر مستند) — أي لم يسبق أحداً إلى زرع بصمة.

**ما كُتب**: لكل معلم `pins/{بصمته}` = `{tid, ts}` ثم `teachers/{tid}.reg = true` بكتابة دمج
على الحقل وحده (`updateMask=reg`). **لم تُحذف `pinHash`** — شبكة أمان للأجهزة التي لم تُحدَّث بعد.
**ولم يُكتب `pt`** — لأن الختم يُبطل الرقم الحالي إن لم يطابق ختمَ مستند البصمة، ولا حاجة إليه هنا.

**الحصيلة**: ٢٤ مُرحَّلاً بالكامل · صفر إخفاق · صفر معلم بلا تسجيل · ٢٤ مستند بصمة لا غريب فيها ·
صفر `pinreq` معلّقة. ومقارنة المستندات بالنسخة الاحتياطية تقول: الفرق الوحيد في كل مستند
هو إضافة `reg: true`، وصفر بصمة تغيّرت.

النسخ الاحتياطية (خارج المستودع، تحوي بصمات — لا تُرفع إلى git):
`scratchpad/final/backup_teachers_20260906-140716.json` (قبل) و`…-142407.json` (بعد).

### 11-أ · تصحيح لازم في `js/auth.js` اكتُشف بالترحيل

مستندات المعلمين الـ٢٤ الحقيقية **لا تحمل حقل `ts` إطلاقاً** (أُنشئت بسكربت الزرع قبل أن تشترطه
القواعد)، و`teacherShape()` تشترط `request.resource.data.ts is number` في **كل** كتابة — ومع الدمج
تُقاس على المستند بعد الدمج. فكانت كل كتابة من `stampTeacher` تُرفض، ونتيجتها:

> كل معلم من الـ٢٤ يحاول تغيير رقمه يرى «لم يكتمل التغيير — رقمك القديم لا يزال يعمل»،
> وإعادة تعيين المدير تفشل الفشل نفسه. (لا قفل حساب — لكن الميزة معطّلة تماماً.)

التصحيح: `stampTeacher` تُرسل `ts: Date.now()` مع `reg`/`pt`. برهانٌ من المتصفح على المصدر الحي:
كتابة دمج على مستند معلم **بلا** `ts` ⇒ `permission-denied`، والكتابة نفسها **مع** `ts` ⇒ مقبولة.

### 11-ب · شرط نشر لا يُؤجَّل

`cleanDoc` في **الإصدار المنشور اليوم** (`js/admin/teachers.js?v=47`) تكتب مستند المعلم كاملاً
وتُسقط `reg` و`pt` — وبعد الترحيل ترفض القواعد ذلك (`reg` لا يعود `false`). فالنتيجة:

> **ما دامت الحزمة القديمة منشورة، كل تعديل لبيانات معلم من لوحة المدير سيُرفض.**
> الدخول لا يتأثر إطلاقاً (المسار القديم يقرأ `pinHash` وهي باقية) — الأثر محصور في لوحة المدير.

النسخة المحلية من `js/admin/teachers.js` تمرّر `reg` و`pt` كما هما بالفعل، فالإصلاح هو **النشر**.

### 11-ج · حساب المدير لا يستطيع تغيير رقمه بنفسه (مقيس، لا مستنتج)

القسم ٨ يقول إن رقم المدير «صار قابلاً للتغيير من داخل التطبيق». **القواعد المنشورة تمنع ذلك فعلياً.**
اختُبر على الموقع الحي بحساب مدير مؤقت هو صورة طبق الأصل للمدير المُرحَّل:

| المحاولة | النتيجة الفعلية |
|---|---|
| `changePin` للمدير على نفسه | «لم يكتمل التغيير — رقمك القديم لا يزال يعمل» |
| `resetPin` للمدير على نفسه | الرسالة نفسها |
| الرقم القديم بعدهما | يعمل · والرقم الجديد لا يعمل · ومستند بصمة حي واحد فقط (التراجع سليم، لا رقمان صالحان) |

السببان في `allow update` على `teachers/{tid}`: (١) على حساب المدير يُمنع تغيير `pt` منعاً مطلقاً،
و`stampTeacher` تكتبه في كل تغيير؛ (٢) بصمة المدير `pinHash` لا تُمسّ من العميل، و`stampTeacher`
تطلب إزالتها. فالسلوك سليم وآمن (لا قفل حساب ولا نصف حالة) — لكن الميزة غائبة عن المدير وحده.

**التعديل المطلوب في القواعد** (يُنفّذه من يملك `firestore.rules`) — يكفي شيئان:

```
      // (١) على حساب المدير: امنع تغيير reg فقط، ودع pt لبند قناة الإثبات أعلاه
      //     (إنشاء pinreq لأي معلم يشترط أصلاً معرفة رقم مديرٍ حقيقي، فلا ثغرة)
      && (resource.data.get('admin', false) == false
          || request.resource.data.get('reg', false) == resource.data.get('reg', false));
      // (٢) اسمح بإزالة البصمة للجميع (بما فيهم المدير)، وامنع كتابة بصمة جديدة كما هي اليوم
      && (request.resource.data.get('pinHash', '') == resource.data.get('pinHash', '')
          || request.resource.data.get('pinHash', '') == ''
          || (resource.data.get('admin', false) == false
              && request.resource.data.get('pinHash', '').matches('^[0-9a-f]{64}$')))
```

الإزالة للمدير غير خطرة بعد الترحيل: دخوله صار عبر `pins`، وأقصى ما يفعله عابثٌ هو مسح بصمة
لم تعد تُستعمل (وهي محذوفة أصلاً في المرحلة (د)). وما يبقى ممنوعاً هو الأخطر: كتابة بصمة جديدة.

**إلى أن يُنشر هذا التعديل**: رقم المدير يُغيَّر بصلاحية المالك وحدها — تُكتب `pins/{بصمة الرقم الجديد}`
= `{tid, ts}` بختم جديد، ثم `teachers/{tid}.pt = ts` نفسه، ثم تُحذف مستند البصمة القديمة.
والبصمة تُحسب `sha256(الرقم + "|" + معرّف المدير + "|" + الملح)`.

> وللعلم: لو ضاع رقم المدير كلياً فلا سبيل لاستعادته من التطبيق إطلاقاً — إنشاء أول بصمة بلا إثبات
> مقصورٌ على حساب `admin == false`، وقناة الإثبات تشترط معرفة رقم مديرٍ أصلاً. الاستعادة بصلاحية
> المالك فقط، بالخطوات الثلاث أعلاه. (النص في القسم ٨ عن «احذف reg وpt ثم registerFirst» لا يعمل.)

## 12. خطة التشديد اللاحقة — متى تُحذف `pinHash` ويُغلق المسار القديم

الترحيل أغلق **النسخ**: لم تعد بصمة أي معلم تُقرأ من مستند مقروء للجميع. لكنه لا يُلغي ما مضى:
من نسخ مجموعة المعلمين قبل اليوم يملك ٢٤ بصمة، ورقم من أربع خانات يُكسر منها على جهازه في ثوانٍ.
**لذلك تدوير الأرقام ليس تحسيناً، بل هو تمام الترحيل** — وهو أيضاً ما يُفرغ `pinHash` من نفسه،
لأن `changePin`/`resetPin` تمسحها من مستند المعلم عند كل تغيير ناجح.

| المرحلة | الشرط الذي يفتحها (قابل للقياس) | العمل | التحقق |
|---|---|---|---|
| **أ — تمّت** | — | `pins` + `reg=true` لـ٢٤، و`pinHash` باقية | ٢٤/٢٤ · صفر غريب · صفر `pinreq` |
| **ب — فوراً** | لا شيء | انشر الحزمة الجديدة (`auth.js` + `index.html`) | تعديل معلم من لوحة المدير ينجح ثانيةً |
| **ج — تدوير** | مضى على (ب) أسبوع ودخل الجميع | كل معلم يغيّر رقمه إلى **٦ خانات فأكثر**؛ ومن لم يفعل يعيد المدير تعيين رقمه | عدّاد «بلا ختم `pt`» يصل إلى صفر |
| **د — الحذف** | `pinHash` = صفر عند غير المدير | احذف بصمة المدير بصلاحية المالك (القواعد تمنع العميل من مسّها) | صفر `pinHash` في المجموعة كلها |
| **هـ — الإغلاق** | صفر `pinHash` منذ ٧ أيام على الأقل | انشر القواعد النهائية (احذف بند ٦-د) | تُطبع `Deploy complete` |

**عدّاد المرحلة (ج)**: `pt` لا يُكتب إلا في تغيير أو إعادة تعيين ناجحة، فوجوده على مستند معلم
دليلٌ قاطع أن رقمه دُوِّر بعد الترحيل، وأن `pinHash` مُسحت من مستنده. لا يحتاج العدّ إلى أي تتبّع.

**أداة المرحلة (د)**: `scratchpad/final/drop_pinhash.py` — يفحص أولاً (`check`)، ولا يحذف إلا بأمر
`drop --confirm-rotation-done`، ويرفض العمل إن بقي معلم بلا `pt` أو بلا مستند بصمة سليم.

**ما يُغلق في المرحلة (هـ)**: بند ٦-د وحده. ويُنصح **بإبقاء** شرط `resource.admin == false` على فرع
إزالة البصمة في ٦-ج أيضاً، فلا يستطيع زائر مسح بصمة المدير عبثاً؛ وبصمة المدير تُحذف بالسكربت.
ثم — بعد أسبوع من استقرار المرحلة (هـ) — تُحذف `'pinHash'` من قائمة `hasOnly` في `teacherShape()`،
ويُحذف السقوط إلى `pinHash` من `verify` في `js/auth.js` (يصير كوداً ميتاً).

**علامة العودة للخلف**: قبل المرحلة (هـ) يكفي إعادة نشر القواعد السابقة. بعد حذف `pinHash` لا رجعة
إلا بالنسخة الاحتياطية أعلاه (استعادتها تعمل ما دام بند ٦-د منشوراً)، فلا تُحذف قبل تحقق شرط (د).

**خطر واحد يجب ألا يُنسى**: حذف `pinHash` يقفل أي جهاز ما زال يحمل الحزمة القديمة في الذاكرة
(يقول «لم تُسجل هويتك بعد»). `sw.js` شبكةٌ أولاً، فإعادة فتح الصفحة كافية — لكن لا تُنفَّذ المرحلة
(د) في يوم امتحان أو مناسبة، ويُفضّل تنفيذها في إجازة نهاية الأسبوع.
